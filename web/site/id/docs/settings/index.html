Mengubah pengaturan

komando config show                          # setiap pengaturan: KEY VALUE DEFAULT ALLOWED, dan di mana file berada
komando config get parallel
komando config set parallel 20
komando config set default_timeout 10m
komando doctor                               # periksa pengaturan, inventaris, dan keamanannya

Jika diketik tanpa argumen, komando config set menanyakan pengaturannya, lalu nilainya.

config set menyatakan apa yang berubah:

parallel: 10 → 20

Di JSON, config show memberi setiap pengaturan di data.keys.

Perubahan yang mematikan sebuah pemeriksaan bertanya dulu kepada Anda di terminal (This turns off a komando safety check: ... Continue? [y/N]); agen AI atau script menambahkan --yes setelah seseorang setuju. Lihat Apa yang butuh jawaban ya.

komando config set host_key_policy strict    # tolak server yang belum Anda percayai
komando config set audit_sql hash            # jauhkan teks SQL dari riwayat
komando config set vpn_idle 0                # jangan pernah menutup VPN karena tidak terpakai
komando config set audit_syslog tls://siem.example:6514   # juga kirim audit ke server log (komando bertanya dulu)

Dengan audit_syslog diatur, setiap record audit juga dikirim ke server log saat ditulis: syslog (RFC 5424, facility authpriv, program komando, message id audit, JSON record sebagai pesan) lewat UDP, TCP, atau TLS. Log lokal tetap menjadi catatannya: bila server log tidak menjawab, komando menyatakannya sekali di stderr dan perintah dilanjutkan. Salinan di mesin lain menjaga riwayat bahkan bila seseorang dengan akun user Anda menulis ulang file lokal.

Nilai negatif ditolak. Setiap perubahan dicatat di komando audit dengan nilai lama dan barunya.

Sebagian besar pengaturan juga punya flag untuk sekali jalan: --timeout, --connect-timeout, --parallel (-P), --max-output, dan --host-key-policy. Bila tidak disebut, flag mengambil dari pengaturan: komando schema menampilkan flag seperti itu dengan "default": "0" (tidak diberikan) dan "default_from": "setting:default_timeout" (pengaturan yang dibacanya).

--host-key-policy menerima accept-new, strict, atau off (huruf besar atau kecil); selain itu adalah error USAGE, tidak pernah pemeriksaan yang lebih longgar. Flag yang lebih longgar daripada pengaturan host_key_policy (accept-new saat pengaturannya strict, atau off) butuh jawaban ya yang sama dengan melonggarkan pengaturan lewat config set: SAFETY_SETTING untuk agen AI atau script tanpa --yes. --dry-run milik agen tersambung dengan pengaturannya.

Meminta kode sebelum perintah berisiko dari agen

Saat agen AI menambahkan --yes, --allow-dangerous, atau --reveal, komando membuka jendela "Allow once" di layar Anda (lihat Keamanan). Agar butuh lebih dari satu klik, nyalakan kode persetujuan: jendela lalu juga meminta kode 6 digit dari aplikasi authenticator di ponsel Anda.

komando config approval-code             # menampilkan secret untuk ditambahkan ke aplikasi authenticator Anda
komando config approval-code --off       # matikan lagi (komando bertanya dulu)

Di desktop Linux atau BSD, kodenya wajib: program Anda yang lain bisa menekan tombol jendela di sana, jadi tanpa kode komando tidak membuka jendela dan agen meminta Anda menjalankan perintahnya sendiri.

Setiap kode hanya berlaku sekali. komando mengingat, di store tersegelnya, kode terakhir yang diterimanya; kode yang sama, atau yang lebih lama, tidak mengizinkan jendela kedua, bahkan dalam 30 detik yang sama. Tunggu kode berikutnya yang ditampilkan aplikasi Anda. Kode yang Anda ketik saat menyalakannya juga dihitung terpakai.

Hanya orang di terminal yang bisa menyalakannya: secret ditampilkan sekali, di sana. Mematikannya adalah jawaban ya seperti perubahan keamanan lainnya, jadi untuk agen AI butuh jendela dan kodenya juga. komando config show menyatakan apakah kode itu menyala.

Di Windows, jendela hanya menghitung klik atau penekanan tombol dari mouse atau keyboard sungguhan: program lain tidak bisa menekan "Allow once" untuk Anda. Ini juga berarti screen reader atau tool lain yang menekan tombol untuk Anda tidak bisa menekannya. Di macOS, program yang punya izin Accessibility (System Settings, Privacy & Security) bisa mengklik tombol di jendela mana pun, termasuk yang ini. Jangan berikan izin itu kepada terminal tempat agen bekerja, atau nyalakan kode persetujuan.

Tempat komando menyimpan datanya

Semuanya ada di ~/.komando/ (di Windows %USERPROFILE%\.komando; ubah dengan KOMANDO_HOME). Hanya Anda yang bisa membacanya:

  • macOS dan Linux: foldernya bermode 0700 dan file-nya 0600.
  • Windows: mode file tidak berfungsi di sana, jadi komando memberi folder itu daftar akses tersendiri: hanya user Anda dan sistem, diteruskan ke setiap file di dalamnya. komando doctor memperingatkan file apa pun yang bisa dibuka orang lain, dan mencetak perintah icacls yang memperbaikinya.

komando menyimpan data Anda tersegel dalam satu file:

FileIsinya
store.dbserver, conn, VPN, key, recipe, pengaturan, secret, fingerprint server yang diingat, dan riwayat setiap tindakan, tiap record tersegel (AES-256-GCM). Hanya ID acak, jenis, versi, dan waktu perubahan yang bisa dibaca tanpa key
store.keykey store, hanya bila tidak ada keychain (tidak ada bila key ada di keychain atau Anda memakai KOMANDO_VAULT_PASS)
store.madecatatan bahwa folder ini pernah punya store. komando menulisnya bersama store dan menyimpannya, sehingga store.db yang hilang diketahui (di bawah). Tidak berisi secret
runtime.jsonjob, tunnel, login server, dan sesi VPN yang dimulai komando (disegel dengan key store; hanya terbuka dengan tanda yang disimpan store.db untuknya, sehingga salinan lama yang dikembalikan terbaca kosong)
runtime.pidshanya process ID pekerjaan latar belakang komando sendiri, sehingga komando bisa tahu apakah masih berjalan tanpa membuka store
vpn/, tunnels/, login/log VPN, tunnel, dan login server (yang tidak dipakai apa pun yang berjalan dihapus setelah seminggu), dan status klien VPN bawaan

Salin store.db hanya saat komando tidak menjalankan apa pun, kalau tidak salinan yang diambil saat ada perubahan bisa rusak. Backup folder ini dan jaga tetap privat.

komando hanya membaca store.db. Folder yang pernah punya store tetapi kehilangan store.db berhenti dengan STATE_CORRUPT sampai Anda mengembalikan store.db dari backup. Hal-hal ini menunjukkan folder itu pernah punya store: store.made, store.key atau store.key.new, store.db-journal, runtime.pids, runtime.json yang tersegel, atau hitungan perubahan yang disimpan keychain untuk folder itu. Setiap store meninggalkan store.made, juga yang key-nya ada di keychain (tanpa store.key); store buatan komando yang lebih lama mendapatkannya saat komando membukanya berikutnya. File lock tidak dihitung: perintah yang ditolak juga meninggalkannya.

Saat key store ada di keychain OS, keychain juga mengingat berapa banyak perubahan yang dialami store. Salinan store.db yang lebih lama yang dikembalikan (dari backup, atau oleh seseorang) menghentikan setiap perintah dengan STORE_OLD_COPY, karena server, aturan, secret, atau host key yang di-pin mungkin sudah lama. komando doctor dan dry run tetap berfungsi, dan hanya melihat: tidak menulis apa pun ke salinan lama, dan tidak pernah memulai store baru bila store.db hilang. Bila Anda memulihkan folder dengan sengaja, jalankan komando doctor --accept-old-copy di terminal Anda sendiri.

Dengan key di store.key atau passphrase, store dibandingkan hanya bila keychain menyimpan hitungan untuk folder ini: berarti itu backup dari sebelum komando secret keychain. Bila keychain tidak bisa menyatakan apakah ia menyimpannya (terkunci, atau tidak menjawab), komando membaca store seperti itu tetapi tidak mengubah apa pun (KEYCHAIN_FAILED, atau KEYCHAIN_SLOW): mungkin itu backup tersebut. Buka kunci keychain dan jalankan lagi. Di komputer tanpa keychain yang berfungsi, seseorang mengatur KOMANDO_KEYCHAIN=off (off milik agen AI tetap bertanya ke keychain). Bila keychain menjawab bahwa ia tidak menyimpan hitungan, tidak ada yang bisa dibandingkan, dan komando doctor menyatakannya.

Tempat key vault berada

Key store disimpan dengan salah satu dari tiga cara: di keychain OS, di store.key, atau dibuat dari passphrase. komando doctor menyatakan mana yang dipakai, dan komando secret keychain serta komando secret passphrase memindahkan dan mengubahnya (lihat Secret).

Vault baru menyimpan key-nya di keychain OS, sehingga salinan folder ini tidak membuka vault:

  • macOS: keychain, lewat /usr/bin/security.
  • Linux: Secret Service, lewat secret-tool di /usr/bin, /bin, atau /usr/local/bin.
  • Windows: Credential Manager, sebagai kredensial untuk user Anda di komputer ini saja (tidak berpindah ke komputer lain).

komando tidak pernah mencari tool ini di PATH. komando membuat key saat secret pertama Anda, membacanya kembali, dan baru setelah itu mengandalkannya. Key yang sudah dipegang keychain untuk folder ini (dari vault yang Anda pindahkan) dipakai, tidak pernah digantikan.

komando menyimpan key baru hanya bila keychain menyatakan tidak menyimpan apa pun untuk folder ini. Di Linux, collection yang terkunci menyembunyikan key-nya dari pencarian (dan KeePassXC juga menyembunyikannya dari pencarian), sementara secret-tool store meminta membuka kunci collection default lalu menimpa item di sana. Jadi komando lebih dulu menanyakan ke Secret Service, lewat gdbus atau busctl dari folder sistem yang sama, apakah collection default terbuka, dan baru kemudian memeriksa bahwa secret-tool search --all tidak mencantumkan item apa pun.

Bila keychain tidak bisa menyimpan key atau tidak bisa menyatakannya, key masuk ke store.key dan komando doctor memperingatkan. Itu terjadi pada:

  • server Linux tanpa secret-tool atau sesi desktop, collection default yang terkunci, atau tanpa gdbus atau busctl;
  • Mac yang dijangkau lewat SSH dengan keychain terkunci, atau user Mac tanpa keychain default (HOME yang diubah, seperti di bawah sudo -E, sandbox, atau CI: komando menanyakan security default-keychain dulu, sehingga macOS tidak menampilkan dialog "Keychain Not Found");
  • komputer Windows tanpa Credential Manager;
  • item untuk folder ini yang tetap terkunci, container, atau keychain yang tidak menjawab dalam beberapa detik.

Sebelum komando membuat store baru, komando menanyakan ke keychain apakah masih mengingat hitungan perubahan untuk folder ini: berarti folder itu pernah punya store yang dihapus, dan komando tidak memulai store kosong sebagai gantinya (STORE_OLD_COPY, seperti untuk salinan lama di atas). Bila keychain menyatakan tidak punya hitungan, atau sama sekali tidak ada keychain (tanpa secret-tool, tanpa Credential Manager, KOMANDO_KEYCHAIN=off), store baru dimulai seperti di atas.

Bila keychain tidak bisa menyatakan (keychain terkunci lewat SSH, tanpa keychain default untuk HOME ini, tanpa sesi desktop untuk secret-tool, atau tidak menjawab dalam satu detik):

  • Orang atau script di folder yang belum pernah punya store (tidak ada file yang tercantum di Tempat komando menyimpan datanya, termasuk store.made) tetap mendapat store baru. Key-nya masuk ke store.key, tidak pernah keychain, dan komando mencetak satu catatan di stderr: store dijaga hanya oleh file key-nya. Perintah yang membuatnya dilanjutkan. Perintah berikutnya hanya membaca selama keychain tidak bisa dibaca; di komputer tanpa keychain yang berfungsi, atur KOMANDO_KEYCHAIN=off.
  • Perintah agen AI tidak membuat store: STORE_OLD_COPY, atau KEYCHAIN_SLOW bila keychain tidak menjawab tepat waktu. Minta seseorang menjalankan perintah itu sekali di terminalnya sendiri.
  • Di folder yang pernah punya store (store.made, store.key, atau file lain tadi), tidak ada perintah siapa pun yang membuatnya, siapa pun yang menjalankan. Kembalikan store.db dari backup. Untuk sengaja memulai store kosong setelah keychain menjawab, seseorang menjalankan komando doctor --accept-old-copy (bila keychain mengingat hitungan store), atau memindahkan folder itu.

Vault yang key-nya ada di store.key menyimpannya di sana sampai Anda memindahkannya: jalankan komando secret keychain. Ini berfungsi sebelum atau sesudah secret pertama Anda: vault mendapat key baru saat berpindah, disimpan hanya di keychain, sehingga salinan store.key yang dibuat sebelumnya (di backup atau riwayat folder yang disinkronkan) tidak membuka apa pun, bahkan secret yang Anda miliki saat itu (--off memindahkan key kembali ke store.key, dan komando bertanya dulu). Hanya orang di terminal yang bisa menjalankannya: agen AI atau script mendapat NEEDS_PERSON, karena keychain mungkin meminta dibuka kuncinya. Di Linux, perintah berhenti, dan meminta Anda membuka kunci keychain, selama collection default terkunci. Perintah menolak bila keychain sudah memegang key lain untuk folder ini (kemungkinan besar satu-satunya key dari vault yang Anda pindahkan): kembalikan vault itu, atau hapus item dari keychain sendiri setelah tidak ada vault yang membutuhkannya. Vault yang key-nya ada di keychain hanya terbuka di tempat keychain itu tidak terkunci: di Mac yang Anda jangkau lewat SSH, buka kuncinya dulu (security unlock-keychain), atau pakai passphrase.

Bila keychain tidak menjawab dalam beberapa detik, komando tetap membaca store tetapi tidak mengubah apa pun: perintah yang akan mengubah sesuatu berhenti dengan KEYCHAIN_SLOW. Coba lagi sebentar lagi.

Passphrase sebagai ganti keychain

KOMANDO_VAULT_PASS adalah cara lain melindungi vault, terutama untuk komputer tanpa keychain (server Linux tanpa secret-tool). Vault baru menentukan modenya saat secret pertama Anda: dengan variabel diatur sepanjang 15 karakter atau lebih, vault mendapat passphrase itu. Mengatur atau mengubah variabel saja tidak berpengaruh pada vault yang sudah ada; komando secret passphrase yang melakukannya. Vault dengan passphrase butuh passphrase yang sama di setiap shell dan proses latar belakang.

Untuk mengubah passphrase, atau memberi passphrase pada vault yang key-nya ada di store.key atau keychain, jalankan komando secret passphrase di terminal Anda. Perintah menanyakan passphrase baru dua kali (disembunyikan, 15 karakter atau lebih) dan mengenkripsi ulang setiap secret dengannya; bila ada yang tidak bisa didekripsi, tidak ada yang berubah. Bila KOMANDO_VAULT_PASS sudah berisi nilai yang baru, perintah menanyakan yang sekarang. store.key atau item keychain yang lama dihapus hanya setelah vault baru disimpan dan dibaca kembali. Lalu taruh passphrase baru di KOMANDO_VAULT_PASS di setiap tempat Anda mengaturnya, dan mulai ulang tunnel dan sesi VPN latar belakang: keduanya masih memegang key lama. --off kembali ke key acak baru di store.key (komando bertanya dulu). Hanya orang di terminal yang bisa menjalankannya, tidak pernah agen AI. KOMANDO_VAULT_PASS yang diubah tanpanya tidak membuka secret apa pun (tidak ada yang hilang: atur lagi nilai yang lama); komando doctor menyatakannya.

Untuk pindah ke komputer lain, lihat Pindah ke komputer lain: komando export (tanpa kata sandi), atau seluruh folder setelah vault punya passphrase.

Update komando

Untuk memperbarui komando itu sendiri, lihat Instal, update, hapus.

Batasan

  • Keychain menjauhkan key dari orang yang menyalin folder ini. Keychain tidak menjauhkannya dari program lain yang Anda jalankan sendiri, dan itu termasuk agen AI dengan shell:
    • macOS: komando membaca item lewat /usr/bin/security, jadi program apa pun dari user Anda bisa membacanya dengan cara yang sama, tanpa prompt. Program itu juga bisa menurunkan hitungan perubahan yang disimpan komando di sana, lalu mengembalikan salinan lama store.db tanpa STORE_OLD_COPY. Hanya komando bertanda tangan yang menyimpan item untuk dirinya sendiri yang bisa menutup celah ini.
    • Windows: Credential Manager memberikan item ke program apa pun dari user Anda.
    • Linux: selama keychain tidak terkunci, secret-tool memberikan item ke program apa pun dari user Anda.
  • Aturan komando (secret yang disamarkan, jendela persetujuan, server yang dilindungi) berlaku untuk agen AI yang memakai komando. Program yang berjalan sebagai user Anda sendiri dan mengabaikan aturan itu bisa membuka vault sendiri, bagaimanapun key disimpan: ia membaca store.key, meminta item ke keychain seperti komando, atau membaca KOMANDO_VAULT_PASS dari shell yang memulainya. Hanya dua hal yang menghentikan program seperti itu: menjalankannya sebagai user OS lain (atau di container atau mesin virtual tanpa folder home dan keychain Anda), atau aplikasi Komando untuk Mac yang bertanda tangan, yang menyimpan key untuk dirinya sendiri.
  • Satu kasus yang tidak bisa dilihat komando saat menyimpan key baru: item di database KeePassXC selain yang default, selama database itu terkunci.

STATE_CORRUPT (exit 1)store.db hilang di folder yang pernah punya store, atau tidak terbuka dengan key; atau runtime.json tidak terbukauntuk store.db: kembalikan folder dari backup, lalu komando doctor --accept-old-copy di terminal Anda sendiri; untuk runtime.json: pindahkan dan sambungkan lagi (isinya hanya VPN, login, job, dan tunnel yang berjalan)
KEYCHAIN_SLOW (exit 1)keychain tidak menjawab tepat waktu, jadi tidak ada yang diubahjalankan lagi sebentar lagi; komando doctor bila terus terjadi
VAULT_LOCKED, VAULT_DECRYPT, VAULT_KEY (exit 1)vault tidak terbukalihat Secret
AUDIT_UNAVAILABLE (exit 1)audit log tidak bisa ditulis, jadi tidak ada yang berjalankomando doctor menunjukkan alasannya
