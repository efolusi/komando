Secrets

Save a password, key passphrase or token once, then point to it as secret:NAME instead of typing it. komando shows a saved value only to a person who asks with --reveal (secret show, key show), at a terminal or after "Allow once" in komando's window, and never to an AI agent.

Save a password and use it

komando secret set web1-pass                          # type or paste it after the prompt, nothing is shown
komando host edit web1 --password-ref secret:web1-pass
komando test web1
komando secret list                                   # names, when they changed, what uses them

Typed alone, komando secret set asks for the name, then the value (hidden).

Save one

At your terminal, komando secret set NAME asks for the value and hides it as you type or paste:

Paste or type the value for web1-pass, then press Enter (it stays hidden):

Paste it after the prompt appears. Text typed before it appears was already shown on the screen, so komando does not use it, and says so: Note: what was typed before this question showed was not used. If that text was the secret, clear the screen and type it again. A value of several lines (a key, a certificate) goes in on stdin:

komando secret set web1-pass                   # asks, hidden
komando secret set db-pass --from-env DB_PASS  # from an environment variable
pbpaste | komando secret set vpn-pass          # from the clipboard (xclip -o on Linux)
komando secret set tls-key < server.key        # a value of several lines
  • A value on the command line (komando secret set NAME VALUE) is refused with SECRET_IN_ARGS: it would stay in your shell history.
  • A paste of more than one line at the prompt stops with USAGE and stores nothing: the shell would otherwise run the other lines.
  • An empty value (an empty pipe, an empty variable, Enter at the prompt) stops with USAGE and stores nothing.
  • From a pipe, the line break at the end is not part of the value. Spaces are kept; komando warns when the value starts or ends with one.
  • secret set on a name that exists replaces its value. When a protected server or conn uses it, komando asks you first; an AI agent or a script adds --yes after a person agrees.
  • secret set NAME --new only stores a new secret: when NAME is in the vault already, it stops with SECRET_EXISTS (exit 8) and the stored value stays. The value comes in as without --new. When several komando commands store the same name with --new at once, exactly one stores it and the others stop with SECRET_EXISTS. With --dry-run it says the same: SECRET_EXISTS for a taken name, "action": "would_store" for a free one.
komando secret set api-token --new --from-env TOKEN   # never replaces one

Use one

Every --password-ref, --sudo-ref, --passphrase-ref and VPN key flag takes a reference:

komando host edit web1 --sudo-ref secret:web1-sudo
komando conn add prod-db postgres://app@10.0.0.5/shop --password-ref secret:prod-db-pass
komando key add work ~/.ssh/id_work --passphrase-ref secret:work-pass
komando exec web1 --env DB_PASS=secret:prod-db-pass -- ./migrate.sh
komando fs replace web1 /srv/app/.env --old 'DB_PASSWORD=[hidden]' --new 'DB_PASSWORD={{secret:prod-db-pass}}' --backup

A reference can also read a password your team keeps elsewhere: env:VAR, file:PATH, HashiCorp Vault or OpenBao (vault:PATH#FIELD), AWS, Google and Azure secret managers (aws-sm:, gcp-sm:, azure-kv:), 1Password Connect (op://), Bitwarden or Vaultwarden (bw://) and KeePass files (kdbx:). See Passwords from your password manager for each one and the login it uses. komando reads such a value only when it needs it and never stores it.

Check one

komando secret show web1-pass      # does it exist, what uses it, a warning about spaces (no value)
komando secret check web1-pass     # type the value you think it is: match or how they differ

secret check never shows either value: it says whether they match, or whether they differ only in spaces at the ends, only in upper and lower case, or in length. Only a person can run it.

See a value again

komando secret show web1-pass --reveal            # print it (a person, at a terminal)
komando secret show web1-pass --reveal | pbcopy   # or copy it
komando key show deploy --reveal > deploy.key     # the private key of a key komando made
  • At a terminal komando prints the value: you typed the command.
  • From a program without a terminal, such as the Komando Mac app, komando first asks you in its own window, naming the secret, the command and the programs that started it ("Started from: Komando"). It shows the value only after Allow once; with komando config approval-code on, the window also asks for the 6-digit code. A Linux or BSD desktop gets that window only with the approval code, and with no screen it stops with REVEAL_NEEDS_TERMINAL: run it in a terminal.
  • An AI agent never gets a value or a private key, not even with your yes: komando refuses with REVEAL_NEEDS_TERMINAL and opens no window. The agent uses secret:NAME in a command instead. A key through ssh-gate (the iPhone and iPad app) is refused too.
  • A dry run shows no value and asks nobody.
  • Every value shown goes in the audit log, as secret.reveal or key.reveal, with how you allowed it (via: terminal or window) and the programs that started komando (started_from); every refusal goes there too, with the secret's or key's name. The value never does.
  • key show --reveal prints only keys komando made (key gen), which it keeps in its sealed store; for a key added from a file it names that file.

Rename, copy and remove

komando secret rename vpn-password office-vpn-pass --dry-run   # what would change
komando secret rename vpn-password office-vpn-pass             # every server, conn, key and VPN follows
komando secret cp db-pass db-pass-old                          # a copy; nothing else changes
komando secret rm old-pass other-old-pass                      # all of them, or none
  • secret rename points every server, conn, key and VPN that used secret:OLD at secret:NEW in the same step (conn URL options such as ?ca=secret:OLD too). Scripts and files of your own are not changed.
  • When NEW exists, add --overwrite; what uses NEW then gets the value of OLD. When a protected server or conn uses NEW, komando asks you first (--yes for an AI agent or a script).
  • secret rm is refused while anything uses a name (SECRET_IN_USE lists what does); point those at another secret first, or rename it.
  • A deleted secret has no copy, so at your terminal you type the secret's name first (several: how many). An AI agent or a script adds --allow-dangerous after a person agrees (POLICY_BLOCKED otherwise).

Where they are kept, and the key

Secrets are sealed with AES-256-GCM in ~/.komando/store.db. The key that opens them is in the OS keychain (macOS keychain, Linux Secret Service, Windows Credential Manager), or in ~/.komando/store.key where there is no keychain, or comes from a passphrase in KOMANDO_VAULT_PASS.

komando doctor                       # which of the three is in use, and any warning
komando secret keychain              # move the key from store.key into the keychain
komando secret keychain --off        # move it back into store.key (komando asks first)
komando secret passphrase            # give the store a passphrase, or change it
komando secret passphrase --off      # back to a random key in store.key (komando asks first)
komando secret passphrase --dry-run

komando uses the keychain on its own only when a new store makes its key, and to keep the store's change count beside a key that is there. It leaves the keychain alone with KOMANDO_KEYCHAIN=off (CI, containers, test runs), where there is no keychain tool, and on a Mac whose user has no default keychain (a changed HOME): the key then goes into store.key, and komando doctor says so. It never makes macOS ask where to keep it. An AI agent's KOMANDO_KEYCHAIN=off still lets komando read and raise the change count: an agent cannot switch off the old-copy check that way. Nor can an agent point komando at another keychain: its KOMANDO_KEYCHAIN path (a keychain file on a Mac) is not used, so its calls keep the key and the count in the login keychain. A store whose key is in your own keychain file is opened only by your commands.

These commands change where the key is, so only a person at a terminal runs them (NEEDS_PERSON for an AI agent or a script); --dry-run previews them for anyone. --off turns a check off, so komando asks first; a script adds --yes. Details: Settings and files.

komando takes KOMANDO_VAULT_PASS and the password managers' unlock variables out of its environment when it starts, so no program it runs inherits them (see Environment variables).

For AI agents

An agent never sees a value: output shows [secret:NAME] or [hidden].

The agent wants toIt runsOr it gets
store a password the user knowsasks the user to run komando secret set NAMENEEDS_PERSON
store a token a program madeecho "$TOKEN" | komando secret set NAME or --from-env VAR
preview a changethe same command with --dry-runmeta.would_be_blocked names what the real run needs
use a secretsecret:NAME in a flagSECRET_DESTINATION: a person allows where it goes
rename, copy, removesecret rename, secret cp, secret rm
read or compare a valueasks the user (secret show --reveal, key show --reveal, secret check)REVEAL_NEEDS_TERMINAL, NEEDS_PERSON

The agent never asks for a password in the chat: the hint names the command the user runs in their own terminal.

Limits

  • Hiding a value in a server's output is a best effort (see Safety).
  • A secret from a password manager (vault:, op:// ...) is read when needed and never stored, so that manager must be reachable each time.
  • A vault whose key is in the keychain opens only where that keychain is unlocked. A copied folder opens its secrets only with a passphrase (see Move to another computer).
  • Anything that runs as your own user can reach the key; see Settings and files.
