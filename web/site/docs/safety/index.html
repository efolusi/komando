Protect production

Mark a server or conn as protected, and komando asks before every change on it:

komando host edit web1 --protected        # komando asks before every change on web1
komando conn edit prod-db --protected     # the same for a database
komando policy check 'rm -rf /'           # would this be blocked? (exit 6 if so)
komando audit -o text                     # what was done, and by whom

Typed alone, komando host edit asks for the server, then what to change.

When you change web1 later, komando asks first:

web1 (protected): this command changes it. Continue? [y/N]

An AI agent or a script is not asked: it adds --yes after a person agrees (see When you are at the terminal).

The seatbelts

SeatbeltWhat it does
Dangerous-command filterBlocks commands such as rm -rf /, mkfs, reboot, DROP DATABASE, curl … | sh, flushing the firewall and stopping SSH, on your servers, in pods and in databases. See them all with komando policy list.
Protected servers and connsAny change on it needs a yes. For the entry itself that means re-pointing it (address, port, user, key, password, --via), replacing a secret it uses (a protected VPN's key, pre-shared key or profile too), renaming it, removing it and turning protection off; its tags, groups, labels and notes change without one. Commands that only look can say so with --read-only and run without a yes. Anything at the same address and port (a user@address target, a second name, a name that resolves to the same IP, a second conn to the same database server, the SSH server behind a protected sftp:// conn) is protected too, whichever VPN or bastion it goes through. With many targets, komando checks all of them before it runs anything: one protected target stops the whole command before the first one runs (at a terminal, komando asks once), and the error names every protected target. A command never stops halfway because of protection.
Read-only by defaultdb query, cache run and cluster run only read unless you add --write. On PostgreSQL, MySQL, Oracle and ClickHouse the database itself enforces it (a read-only transaction, or ClickHouse's readonly=1); SQL Server always rolls the SQL back. On Snowflake, BigQuery and MongoDB komando's own check of each statement keeps it a read: for a hard guarantee, connect with a user that may only read. See databases.
Dry run--dry-run shows what would run and whether it would be blocked (meta.would_be_blocked). It is never blocked itself, with one exception: an AI agent's command with KOMANDO_HOME set to another folder stops, dry run or not (see the usual data folder, below). It never opens the approval window, so for an AI agent --reveal does not count in a dry run (output stays masked), and an agent's preview connects with --host-key-policy off ignored.
Safety settingsTurning off the audit log or server identity checks, moving the vault key out of the keychain, removing a deny rule, or an AI agent setting a --proxy-command (a program on this computer) needs a yes.
Server identityIf a server's fingerprint changes, komando refuses to connect (HOSTKEY_MISMATCH).
Safe editsFile edits replace exactly the text you name, write the whole file at once (never half-written), and can keep a .bak backup. As root (--sudo), komando follows no link another server user made, and does not write into a folder another user can change, since that user could swap the file for a link while root writes (SHARED_FOLDER_CONFLICT).
Sealed vaultPasswords are sealed with AES-256-GCM, with the key in the OS keychain (or, where there is none, in a file beside the store; komando doctor warns). Only names are ever shown. Only a person can see a value: at a terminal, or from the Komando Mac app after Allow once in komando's window (secret show --reveal, key show --reveal); an AI agent never can, and every value shown is in the audit log (See a value again). secret rename and secret cp rename and copy inside the vault, so a value never has to be shown or typed again. secret check lets a person compare a value without showing it. The approval code's key can only be changed with komando config approval-code (RESERVED_SECRET). See Secrets.
Secrets hidden in outputIf a vault secret shows up in what a server sends back (a .env file, a log line, env), komando prints [secret:NAME] instead, also when it is base64- or URL-encoded. Values shorter than 6 characters are not hidden. So that this hiding cannot tell an AI agent which of its guesses is a secret, a vault value in an agent's own arguments, script or input is not hidden in that command's output, and the command answers as it would for any other value; it is written to the audit log, where you see the guessing.
HistoryEvery action is in komando audit (see below).

When you are at the terminal

Who is asked depends on who runs the command:

  • You, at a terminal: komando asks you first, and runs the command only after your answer.
  • An AI agent or a script: komando never asks. The command stops with exit 6 and a code (PROTECTED_TARGET, POLICY_BLOCKED ...), and the hint names the flag the real run needs: --yes, or --allow-dangerous for a step that cannot be undone. The agent or script adds that flag after a person agrees.
  • An AI agent that adds the flag: komando opens an "Allow once" window on your screen, and the command runs only when you click it (see Seatbelts for AI agents). A script's flag counts as it is.
  • A CI job (CI set) is never a person, even on a terminal: nothing is asked there.

At a terminal komando asks in one of three ways:

  • A change on a protected server, conn or VPN: web1 (protected): this command changes it. Continue? [y/N].
  • A step that cannot be undone: This <what it does>., and you type the name of what goes: the key, file, secret, topic or image when one goes (Type the name session:42 to continue), how many when several go (Type 37 (objects under daily/ in backups) to continue), or the server's or conn's name for a step on the whole target (a reboot, a restore, a command the filter blocks). Never the word yes. On a protected target the same question says so, and your answer covers the protection too: komando asks once.
  • A change that turns off one of komando's own checks (config set audit off, host_key_policy off, removing a deny rule, going back to an older komando): This turns off a komando safety check: <what>. Continue? [y/N].

More about the questions:

  • A --proxy-command or a cluster's login program that matches a rule says Blocked by policy: ... and asks you to type the server's or conn's name to run it anyway, this once.
  • When komando asked you for a missing argument, it asks Run it? [y/N, d = --dry-run first] before the command runs. One that cannot be undone (deleting data or files, a reboot, stopping sshd, sync --delete) then asks you to type the name of what goes, once. cron rm, pkg rm and db kill need nothing more from an AI agent, but you type the name of what goes instead of answering Run it?. One rule table decides which: every command that stops an AI agent as dangerous asks you for the name.
  • No is the default; Enter or Ctrl-D is a no, and nothing runs. A no exits 6, like a stop: Cancelled. Nothing was changed. (DECLINED when komando asked before the command ran, else the stop's own code). Ctrl-C stops komando there instead: Stopped., exit 1 (CANCELLED).
  • A yes counts for that one command only, as --yes or --allow-dangerous would, and komando audit records it with confirm: tty and what you said yes to.
  • Some stops have no flag and are never asked: HOSTKEY_MISMATCH, NEEDS_PERSON, SSH_GATE_NETWORK_REQUIRED, SSH_GATE_READ_ONLY, SSH_GATE_REFUSED, STORE_OLD_COPY and REVEAL_NEEDS_TERMINAL. Only a person runs those commands, in their own terminal.

Every stop a flag lifts has the same hint, naming every flag the real run needs: an AI agent reads check with --dry-run, ask the user; once they agree, run it again with --yes, a script gets its own command line with the flags filled in.

Seatbelts for AI agents

komando recognizes Claude Code, Codex, Gemini CLI and Cursor by the environment variables they set (a variable that is there counts, whatever its value, also 0 or empty), and adds these rules for them. For any other agent, set KOMANDO_AGENT=1 (or AI_AGENT=1) in the environment it runs commands in, so these rules apply to it too. Scripts and you at your terminal are not affected by them.

SeatbeltWhat it does
A person allows the risky flagsWhen an agent adds --yes, --allow-dangerous or --reveal, komando opens a window on your screen with the whole command, why komando stops it (the matched rule, the protected servers), the servers it runs on and, when the command line does not show it, the program on this computer it lets run. For exec --script FILE, job start --script FILE and exec --stdin-file FILE it also shows the file's SHA-256 and every line of it, never a part: a file longer than 40 lines (long lines wrapped at 100 characters) or 16 KB, one that is not valid text or holds bidi or zero-width characters, and one that looks like it holds a password, key or token gets no window, and the agent asks you to run the command yourself. The SQL of db query --file is shown the same way, and so is the command a recipe fills in (recipe run), with a note when it runs with sudo: a saved recipe can be replaced between two runs, so you allow what runs, not a name. Content a command stores or sends from a file or from stdin (fs write --from, cluster apply --file, queue send --from, an upload with cp, upload or storage upload, the -f and --from-file files of cluster run, a pg_dump archive for db restore) is shown whole when it fits. A named file that is only too long, or is not text (an archive, an image), is named by its size and SHA-256, with a note that its content is not shown, so you can check the file first; content on stdin that is too long, and content that holds invisible characters or looks like it holds a password, gets no window. A folder (cp -r, sync) is shown as the list of its files, each with its size and SHA-256; a list longer than 40 lines gets no window. The plain SQL of db restore is code, like db query --file: shown whole (a .gz unpacked) or no window. Indentation past 16 spaces is named as (+N), so deep YAML keeps its nesting. import checks the secrets it would replace the way secret set does. Your yes covers what that window showed: when a later check of the same command brings a script, a rule or a protected target the window did not have, komando asks again, with it in the window. A yes to --reveal and a yes to --yes or --allow-dangerous never answer for each other. A destructive change on a protected target asks once, in a window that names both flags. It runs only when you click Allow once. Line breaks, tabs, control characters, long runs of spaces and characters that draw nothing show as escapes ($'a:\n b: 1', \u3164), which your shell reads back as the same text. A command that cannot be shown whole (longer than 500 characters, invalid text, or with bidi or zero-width characters) gets no window: the agent is told to make it shorter or ask you to run it. The agent cannot click it. With komando config approval-code, the window also asks for the 6-digit code from your authenticator app, so a click alone is not enough (see Settings). On a Linux or BSD desktop (X11 or Wayland), where another of your programs can press the window's buttons, the code is required: without it komando opens no window, and the agent asks you to turn the code on or to run the command yourself (macOS and Windows keep the plain window). With no screen (an SSH session, a server, KOMANDO_NO_DIALOG set), the agent is refused and asks you to run the command in your own terminal. A window nobody answers closes after 2 minutes; the agent is told nobody answered (not that you clicked Deny) and asks you whether to try again.
Secrets hidden from agentsPasswords, keys and tokens in any output (a .env file, env, a log line, a database row, a Kubernetes Secret, requirepass in redis.conf, private keys, password hashes) show as [hidden]. You and your scripts see the real values.
Personal data hidden from agentsOn protected servers and conns, email addresses, phone numbers, card numbers and IBANs in what an agent reads (a database row, a cache value, a log line, a file) show as [hidden: email], [hidden: phone], [hidden: card] and [hidden: iban]. See Personal data.
Agents can still set secretsfs replace --old 'DB_PASSWORD=[hidden]' --new 'DB_PASSWORD={{secret:db}}' --yes puts the vault value on the server without the agent seeing it, once you allow it in the window. Text that still holds [hidden] is never written over a real file (HIDDEN_VALUE). An agent can rename a secret with secret rename (every reference follows) without seeing it.
A person decides where a secret goesOnce a value is on a server the agent controls, it could come back in a form komando does not recognise (reversed, in hex, cut in pieces). So when an agent sends a secret somewhere, it needs --yes, and the window names the secret and the place (SECRET_DESTINATION): {{secret:NAME}} in fs write and fs replace, exec --env K=secret:NAME and job start --env, db user add and db user passwd, and a password or pre-shared key reference (secret:, env:, file:, ...) that host add, host edit, conn add, conn edit, vpn add, vpn edit or an import attaches to a server, conn or VPN, or a server, conn or VPN with one that moves to another address, port, VPN server, --via path or proxy command. Moving a jump server counts for everything behind it: an agent that gives a server a new address, port, --via or proxy command is asked about each password that other servers and conns send through it. Moving a VPN counts the same way: an agent's vpn edit of its address, portal, server or profile, vpn add --overwrite, an import that replaces it, or a new profile in the vault, is asked about each stored password that servers and conns send through it (their --via way goes through the VPN, jump servers included); a server with only a key sends none. So does a secret that decides whom komando trusts: an agent that replaces an OpenVPN VPN's profile in the vault (secret set, secret cp --overwrite, secret rename --overwrite) is asked as for vpn edit (the window names the new servers), and one that replaces, or makes, the CA certificate a WinRM server or a conn is checked against (?ca=secret:NAME), or points a WinRM server at another one, needs your yes too (SAFETY_SETTING). Edits that keep the place (a tag, a user name) ask nothing. A server's own env value from the vault (host edit --env KEY=secret:NAME) is left out of an agent's commands, with a warning on exec and job start, unless the agent adds --yes and you allow it. A dry run never asks: it keeps {{secret:NAME}} as it is and says what the real run would need.
A person decides about weaker connectionsAn agent that adds a conn whose URL turns the network protection down, or edits one so that it does, needs --yes and your yes in the window (SAFETY_SETTING): sslmode=disable, allow or prefer (PostgreSQL), tls=false, preferred or skip-verify (MySQL), encrypt=false, encrypt=disable or tls=skip-verify (SQL Server), tls=false or tls=skip-verify (Oracle, ClickHouse, registry, FTPS), tls=skip-verify or insecure=1 (Kafka, RabbitMQ, NATS, SQS, Pub/Sub), insecure=1 (FTP, Redis, memcached), an http:// endpoint (BigQuery), and going from rediss://, memcacheds:// or an https endpoint to one without TLS.
The usual data folderKOMANDO_HOME moves komando's data. In a new folder komando would know none of your protected servers, deny rules or pinned host keys, and would write the audit log there. So an agent's command with a KOMANDO_HOME other than ~/.komando stops (NEEDS_PERSON), a dry run too: a preview in another folder would still connect, without your pinned host keys, and would preview nothing real. No flag and no window lets it through, because the approval code you may have switched on is kept in your usual folder, not in that one. komando makes and writes nothing in the other folder, so this stop is in no audit log. The agent is told to take KOMANDO_HOME out and run the command again, which then uses your own folder. komando guide uninstall, which takes the agent guard out, stops the same way. If you keep komando's data elsewhere, make ~/.komando a link to that folder: a link to the same folder counts as ~/.komando. HOME does not move it for an agent: komando takes an agent's home folder from the computer's user database, so HOME=/tmp/x komando ... still uses your ~/.komando (and the guard refuses that line). Setting both, HOME=/tmp/x KOMANDO_HOME=/tmp/x/.komando, is another folder like any other KOMANDO_HOME: it stops. You, at your own terminal, may set HOME, and komando follows it. An account the user database does not know (on Linux komando also asks getent, so LDAP and sssd accounts count) leaves komando nothing to check HOME against: an agent's command then needs your yes in the window (SAFETY_SETTING).
No guessing a secretsecret check, which says whether a value is the stored one, is for people only (NEEDS_PERSON): for an agent it would answer yes or no to guesses. secret show tells an agent only whether the value starts or ends with a space, never its length or a hash of it (a hash of a short password can be guessed offline).
Secret files stay on the serverAn agent cannot copy a file that is secret by its name (.env, private keys, credentials, shadow, ...) to this computer (SENSITIVE_FILE); folder copies leave them out. It can read them with fs cat, masked. A stream to stdout (--to -) keeps the same rules before a byte is written: text with secret values as [hidden], a binary file refused when it holds a vault value, a secret or personal data komando hides, and anything over 16 MB refused, as bytes on stdout cannot be taken back. Any other text file an agent downloads (download, sync, storage download) is saved the way fs cat shows it, with secret values as [hidden], and the result says masked; such a copy is never uploaded back (HIDDEN_VALUE). Binary files and files over 16 MB are copied as they are, unless they hold a vault value, or the target hides personal data from agents (see Personal data).
Secret files stay on this computerkomando does not read ~/.komando, private keys, credential stores or files that are secret by name for an agent when a command takes a local file (--stdin-file, script FILE, uploads, sync, fs write --from, db --file, cluster -f) (SENSITIVE_FILE); folder uploads and sync check each file and leave those out. That holds for the same file by another name: a link, a hard link, or other upper and lower case on macOS. You allow a project secret such as .env with --reveal; komando's own data and /proc/PID/environ never go. Imports (komando import kubeconfig, pgpass, docker, ...) may read credential files, because they put the secrets into komando's vault, which the agent never sees. A file: or env: password reference cannot point at komando's data, a private key, a credential store or the password of a secret store either. No reference, for anyone, reads the approval code's key (RESERVED_SECRET). Nor does an agent's command write there: download, cp, sync (and its --delete), storage download, db dump --to, export --to and cluster cp never save a file into komando's folder, ~/.ssh, ~/.aws, ~/.config/gcloud, ~/.azure, ~/.kube, ~/.docker, ~/.gnupg, ~/.password-store or the keychains, also through a link (SENSITIVE_FILE, no flag: you run such a command in your own terminal).
Guard on this computerkomando guide install adds a guard to Claude Code, and to Cursor, Gemini CLI and Codex where you use them. Before the agent reads a file or runs a shell command, komando checks it and stops reading ~/.komando, private keys, .env files and credential stores (~/.kube, ~/.aws, the keychain), listing all environment variables, changing or clearing the variables komando knows an agent by (CLAUDECODE=0, unset, env -u, env -i, read, sudo komando) or KOMANDO_HOME, setting HOME in front of komando, searching or archiving a folder that holds them (grep -r ~, tar -C ~ ...), and running ssh/scp around komando. It reads relative paths from the agent's working folder, follows cd, and counts a glob such as ~/.komand?/* as the path it could match; quoted patterns (grep '.*' f) are not globs. Skip it with --no-guard.

Add your own rules

komando policy deny 'terraform\s+destroy'           # a Go regular expression; prints its id
komando policy list                                  # built-in rules and your deny rules, with ids
komando policy rm 'terraform\s+destroy'              # remove it again
komando policy rm custom-1a2b3c4d                    # or remove it by its id
komando policy check 'terraform destroy'             # exit 6 when it would be blocked
komando policy check --conn-kind postgres 'delete from users'   # rate SQL, Redis or MongoDB instead

A rule matches the command the way the shell reads it, so quotes and backslashes inside a word (r\m, /e""tc) do not hide it. A custom pattern that is not a valid regular expression blocks every command until you fix or remove it; komando doctor and policy list name it.

Built-in rules cannot be removed. A custom rule's id (custom- and eight letters and digits) is made from its pattern, so it stays the same when another rule is removed. A pattern that matches empty text (.*) is refused: it would block every command. Removing a rule turns a check off, so komando asks first (a script adds --yes).

policy check exits 6 when the command would be blocked, so it works in an if. --conn-kind rates a statement for a conn kind instead: postgres, mysql, sqlserver, oracle, clickhouse, snowflake, bigquery, sqlite, redis, memcached or mongodb (a command document as JSON). It exits 6 too when the statement is destructive, which db query and cache run refuse without --allow-dangerous.

Personal data

Customer data in production should not end up in an AI model. On protected servers and conns, an AI agent sees personal data hidden in what it reads from them: db query rows (also with -o csv), cache get and cache run, storage cat, fs cat, exec, logs and the other commands that show data from a server or resource. komando's own inventory (server addresses, conn URLs) is never hidden.

Shown asWhat komando looks for
[hidden: email]an email address (not git@... or noreply@...)
[hidden: phone]a phone number in international form: +, the country code, 8 to 15 digits
[hidden: card]a payment card number: a card network's first digits, its length, and a valid check digit
[hidden: iban]an IBAN with valid check digits
[hidden: column]any value in a database column you name (below)
komando config set mask_personal all             # on every server and conn
komando conn edit staging-db --option mask_personal=on   # on this conn, whatever the setting
komando conn edit prod-db --option 'mask_columns=name address birth_date'
komando config set mask_personal protected       # back to the default (komando asks first)
  • The mask_personal setting is protected (the default), all, or off. Showing agents more (all to protected, or off) turns a check off, so komando asks first; a script adds --yes.
  • Names and street addresses have no shape komando can find, so name the columns that hold them in mask_columns, split by spaces. Setting it also turns personal data hiding on for that conn.
  • A query that names a hidden column could rename it (name AS customer), compute from it (upper(name)) or ask about it (WHERE name LIKE 'A%'), and komando cannot tell which results come from it. So an AI agent's db query that names one anywhere stops with REVEAL_NEEDS_PERSON (exit 6): a person allows it with --reveal. SELECT * shows the column as [hidden: column] beside the others. On MongoDB the names are fields, hidden at any depth, and a command that names one stops the same way.
  • This stops ordinary queries, not a database that builds the name while it runs (whole-row values, dynamic SQL, a view that renames the column). For a column an agent must never read, give the conn's database user no right to read it.
  • The same data is not handed over another way. For an AI agent, where personal data is hidden: cp, sync and download save files with it hidden; fs replace, fs write --dry-run, fs restore and docker compose show it hidden; db dump stops with SENSITIVE_FILE (a dump cannot be masked). A value that is not text is shown as base64; when it holds a secret or personal data, the whole value reads [hidden].
  • A file komando cannot show with personal data hidden stops an AI agent's cp, sync, download or cluster cp with SENSITIVE_FILE: a binary file whose text holds a secret or personal data, a binary file over 256 KiB (too large to check), and any file over 16 MiB. A person allows it with --reveal.
  • The hiding follows the database, not the conn's name: a second conn to the same database (same server address and database name) hides as much. A conn to the same server under another address (a host name for an IP, a tunnel's localhost port) is not recognised as the same, nor a SQLite file under another path (~/app.db and its full path, a link, other upper and lower case on macOS). On PostgreSQL the hiding is per database; on MySQL, SQL Server, ClickHouse, MongoDB and the others, whose conns read every database of the server, it covers the whole server.
  • Taking a column out of mask_columns, turning mask_personal off, or replacing (conn add --overwrite, import --overwrite) or removing such a conn shows agents more: an AI agent needs a person's yes for it (SAFETY_SETTING), as for the setting. mask_columns takes column names without the table, and the options are written in lower case.
  • A person decides when an agent sees the real values: with --reveal, which a person allows in the approval window, the agent sees them for that one command.
  • A masked value is never written back: a db query --write, cache set or cache run --write, and a file write, that still holds [hidden: ...] stops with HIDDEN_VALUE.

History

Every action is in the audit log: time, who ran it, which AI agent asked, whether a person allowed it, the targets and the command. Every change to the inventory and to safety settings is there too: servers, conns, groups, keys, secrets (names only), config set (old and new value) and policy deny and policy rm.

komando audit -o text                 # one line per entry, newest 50
komando audit -n 0                    # all entries
komando audit --failed                # only failed or blocked actions
komando audit --target @web           # only these servers or conns
komando audit --command exec          # only one command family
komando audit --since 2h              # everything in the last two hours
komando audit --since yesterday --until today   # all of yesterday
komando audit verify                  # check the chain

Each record carries the hash of the one before, so komando audit verify (and komando doctor) notice a record that was edited, added or removed outside komando. If the audit log cannot be written, komando refuses to run (AUDIT_UNAVAILABLE). Set KOMANDO_ACTOR to choose the name recorded for you or your agent. An agent's environment can set that name to anything, so its records keep the agent itself (agent) and your computer account, read from the system (os_user), and mark the name as the one it claims (actor_claimed); komando audit -o text shows it as Claude Code (as claude). To keep SQL text out of the history, see audit_sql in Settings.

A key that runs komando and nothing else

To reach komando on this computer from another device (the Komando app on your phone, another computer), give that device's SSH key only komando: komando ssh-gate line prints the line for ~/.ssh/authorized_keys.

komando ssh-gate line --name phone ~/phone.pub                  # may read and change
komando ssh-gate line --name phone-read --read-only ~/phone.pub  # only reads, no network
komando ssh-gate line --name phone-net --read-only --network ~/phone.pub  # reads, network checks too

The key asks komando ssh-gate status which it is: ssh-gate answers it itself, with the key's name, read_only and network.

The line starts with restrict,command="/full/path/komando ssh-gate --name phone". Add it to ~/.ssh/authorized_keys of the account komando runs as, instead of the key's plain line. restrict turns off port, agent and X11 forwarding and the terminal (OpenSSH 7.2 or later). For that key, sshd then runs komando ssh-gate whatever the key asks for, and:

SeatbeltWhat it does
Only komandoThe key's command must be one komando command (ssh HOST komando list -o json), with at most KOMANDO_AGENT=NAME before it. ssh-gate splits it into words like a shell, but runs no shell and expands nothing: an unquoted ;, |, &, >, <, $, backquote or line break is refused, and so is $ or a backquote inside double quotes (SSH_GATE_SYNTAX); put such an argument in single quotes. Any other program, a login shell, scp or sftp is refused too (SSH_GATE_REFUSED).
komando treats it as an AI agentSecret values stay [hidden]. --reveal and --allow-dangerous are refused, and so are commands for a person at a terminal (shell, db shell, cluster shell, secret passphrase, secret check, login aws, config approval-code). --yes on a protected target needs a person on this computer, which the key is not: change protected servers here. No approval window opens for a key.
Nothing written hereEvery key, read-only or not, runs commands on servers, never one that writes on this computer: a file it saved here could be ~/.ssh/authorized_keys or a shell startup file. So download and storage download (except --to -, which streams to the key's own output and is a read, allowed for a read-only key too), db dump, export --to, and cp or sync to a folder here (except cp TARGET:PATH -) are refused, and so is any change to komando's own setup: servers, conns, VPNs, groups, settings, policy rules, secrets, keys, recipes, guide install, import, host trust, tunnel start and stop, and update (SSH_GATE_REFUSED). Change those here, as a person. Every key, read-only too, is also refused every command, reads included, on a target that is this computer: a sqlite conn, which is a file here (VACUUM INTO, ATTACH and db restore write any file), and a server, conn or cluster at localhost, a 127.x or ::1 address, a loopback interface (fe80::1%lo0) or this computer's name. Through such a target exec would be a shell here (--read-only is a filter, not a sandbox), logs --file, fs cat and fs list would read any file here, a private key too, and Postgres COPY TO PROGRAM or pg_read_file, Redis CONFIG SET dir and a Kubernetes hostPath volume run programs or read and write files here. For a conn every host in its URL counts, a list (a,b), Postgres ?host= and ?hostaddr=, and a socket path. cluster run -- cp POD:PATH DST and key deploy --set-default are refused too. A change on a target the gate cannot find is refused; a read runs, unless the name is localhost, a loopback address or this computer's own address, as written or as the name resolves (cert check https://localhost, https://ip6-localhost, a public name that points at 127.0.0.1). What such a read dials is checked again when it connects, so a name whose answer changes in between cannot reach this computer either. A change komando adds later is refused until it is known to act on servers only. No key makes komando read a file here either: exec and job start with --script FILE or --stdin-file FILE, db query --file, db restore --from, cluster apply --file, fs write --from, upload, storage upload, cp and sync from a path here, and cluster run -- apply -f, --from-file or cp to a pod are refused (SSH_GATE_REFUSED): the file could be a private key, and the server's answer would hand it back. Send the content on the key's own input instead (--script -).
Read-only keysWith --read-only the key runs only commands komando counts as reads (the kind in komando schema): exec (also with --script), job start, docker exec and cluster exec need --read-only, db query, cache run and cluster run no --write, db explain no --analyze, pkg upgradable no --refresh, pkg security no --refresh, and a recipe must be marked read-only. storage link and cluster forward are changes (kind: change), since they hand out access or open a port here: a read-only key is refused them (SSH_GATE_READ_ONLY), a full key runs them.
Read keys stay off the networkReaching the network is no write, but it is a way out: what a key reads could leave in a URL or a DNS name. So a --read-only key runs only komando's own reads of the servers and conns in your list (fs, logs, facts, status, svc, docker ps, db query, cache run, cluster run, cert check SERVER, ...). It is refused every net command, cert check of a website (https://HOST, HOST:PORT, which komando dials from this computer), and exec, job start, docker exec, cluster exec and recipe run, whose programs (curl, nslookup, ...) can connect anywhere (SSH_GATE_NETWORK_REQUIRED). A read komando adds later is refused until it is known to stay on listed targets. SQL and cache commands that reach another server or a program are writes, so db query and cache run refuse them without --write: Postgres COPY ... TO PROGRAM and dblink, MySQL INTO OUTFILE, LOAD DATA and LOAD_FILE, SQL Server OPENROWSET, OPENQUERY, linked-server names (lnk.db.dbo.t) and the functions that read a file path (\\HOST\share), ClickHouse url(), remote() and s3(), Oracle UTL_HTTP and XML the query builds (a DTD can name a URL), BigQuery EXTERNAL_QUERY, MongoDB $out and $merge, Redis MIGRATE and REPLICAOF. Add --network to the line for a read key that may run them.
Every command in the historyEach command a key runs or is refused is in komando audit: the key's name (ssh_gate), what it sent (ssh_command, secret-looking values hidden), the address it came from (client) and, when refused, why. What the command then changes is recorded as from ssh-gate key NAME. This record is written even when the audit setting is off; when it cannot be written, nothing runs. In komando audit text, line breaks and terminal escapes in what a key sent show as \n and \x1b, so a key cannot add or hide rows.

Give each device its own key and name, so komando audit tells them apart and you can remove one line to lock one device out. The key reaches komando as the account it logs in to: use that account for komando only, or one with only the permissions komando needs.

Limits

An AI agent runs as your own user on your computer. The approval window, the masking and the guard stop mistakes and prompt injection (a web page or a file telling the agent to leak something). They do not stop a program that deliberately hides what it is or edits the guard away: nothing that runs as you can. The guard reads shell lines as text; a script that builds a path from pieces, or starts komando without the agent's variables from another language, gets past it. So:

  • give komando, and so your agent, an SSH user with only the permissions it needs;
  • mark production with komando host edit NAME --protected;
  • keep the vault key in the OS keychain (move a key from store.key there with komando secret keychain), so other people or backups that reach ~/.komando cannot open the vault;
  • give another device's SSH key only komando, with komando ssh-gate line.

More limits:

  • The dangerous-command filter catches common accidents; it is not a complete security boundary.
  • Masking is a best effort: a secret under an unusual name, or shorter than the text around it, can still slip through. Values shorter than 6 characters are not hidden.
  • Personal data hiding is a best effort too: a phone number written without +, or personal data in an image or a binary file, is not found. Hide whole columns where it matters.
  • ssh-gate sees only the address komando keeps for a target (and, for a Kubernetes conn, the conn's URL, not the server in its stored kubeconfig). A key cannot name a target itself: u@HOST or an IP that is not in your list is refused (SSH_GATE_REFUSED), because it could be this computer's own address. A listed server at one of this computer's own network addresses (its LAN IP), or one whose pinned host key is this computer's own SSH host key (/etc/ssh/ssh_host_*_key.pub: a DNS name, a public IP or a port forward that leads back here), is refused like localhost. What komando still cannot tell apart: a conn or cluster that leads back here under another name, and a server here that has no pinned key yet or runs its own SSH server with other keys. Through such a target any key, read-only too, would read files or get a shell here (exec THAT-HOST --read-only -- 'nc -e /bin/sh ...'). Do not list this computer in komando that way: --read-only does not make it safe.
  • A read key without --network still reaches what your servers and databases reach by their own setup: a Postgres foreign table, a MySQL FEDERATED table, a ClickHouse cluster() or dictionary, a Snowflake external function or stage, a BigQuery remote function in the conn's own project, a Kubernetes API server's webhooks. Those go where a person set them up, not where the key names, but a key that can read through them sends its query there too. And komando reads SQL as text: a SQL Server network path built from pieces (CHAR(92)+CHAR(92)+...) and passed to a function komando does not list is not recognized.
  • Secrets are never accepted as command arguments, because they would land in your shell history (SECRET_IN_ARGS). komando secret set NAME asks for the value after the prompt appears; see Secrets.

At your terminal komando asks you first; an AI agent or a script adds --yes (or --allow-dangerous) after a person agrees. The codes below are what an agent or a script gets.
