Security standards

How komando measures up against the international security standards that fit a DevOps tool that holds credentials and is driven by AI agents. · Safety

On this page

  • Check it yourself
  • OWASP ASVS 4.0.3 (Application Security Verification Standard)
  • OWASP Top 10 for LLM Applications (2025)
  • NIST
  • ISO/IEC 27001:2022 Annex A and CIS Controls v8
  • Supply chain: OpenSSF Scorecard and SLSA
  • Limits

This is a self-assessment, checked against the code and tests. It is not a certificate: a certificate (ISO 27001, SOC 2) is given to an organization for how it works, and komando can only give you controls to use there.

The status column says met, partly met (with the gap named) or yours to do (a step only you can take).

Check it yourself

komando doctor          # security: permissions, vault, audit chain, unencrypted conns
komando audit verify    # nobody edited the audit log
make lint security      # staticcheck, govulncheck (run in a copy of the source code)
make fuzz               # fuzz the parsers that read untrusted text

OWASP ASVS 4.0.3 (Application Security Verification Standard)

RequirementHow komando meets itStatus
2.10, 6.4 Secrets are not in code, arguments or historyVault, secret:NAME references, external managers (HashiCorp Vault/OpenBao, AWS and Google Secret Manager, Azure Key Vault, Bitwarden, KeePass, 1Password Connect); secret values on a command line are refusedMet
6.2 Approved algorithms, no home-made cryptoAES-256-GCM (each value bound to its name), scrypt N=2^17 r=8 p=1, crypto/rand, Ed25519 keys, Go's SSH and TLSMet
6.4.2 Key material is protectedEverything komando keeps is sealed in one file (store.db, AES-256-GCM per record). A new vault keeps its key in the OS keychain (macOS keychain, Linux Secret Service, Windows Credential Manager), read back before it counts; passphrase mode keeps no key on disk; where neither is there, a key file readable only by you (mode 0600 in a 0700 folder, or an owner-only access list on Windows); komando secret keychain moves a key from that file into the keychainMet with the keychain or a passphrase. Partly met without a keychain: the key file sits next to the vault (doctor warns)
4.1.3, 4.3.1 Least privilege, administrative interfaceskomando ssh-gate limits another device's SSH key to komando: no shell or forwarding, agent rules, nothing written on the komando computer (nor through a sqlite file, and nothing, a read either, on a target at a loopback address), --read-only keys run only reads, and only those that stay on listed servers and conns unless the line has --network, every command audited with the key's nameMet. Yours to do: add phone keys with komando ssh-gate line
7.1 Logs record who, what, where, result, without secretsEvery action: time, actor, AI agent, approval, hosts, command; tested to hold no passwordMet
7.3 Logs are protected from changeThe audit log is sealed in store.db, a hash chain that komando audit verify checks; with the key in the keychain, an old copy of the store put back stops every command (STORE_OLD_COPY); and each record can go to a log server with audit_syslogMet with audit_syslog. Partly met without it: the same user can rebuild the chain or cut its end
8.3 Sensitive data is not shown to those who should not see itVault values hidden for everyone; passwords, keys and tokens hidden for AI agents komando recognisesPartly met: masking is a best effort, and an unusual name can slip through
9.1, 9.2 Connections are encrypted and the server is checkedSSH host keys (stop on mismatch; the first key is shown with its fingerprint); SSH asks first for the post-quantum hybrid key exchange mlkem768x25519-sha256 (OpenSSH 10's default, also in OpenSSH 9.9), then curve25519; TLS 1.2+ for Redis, Kubernetes, FTPS, HashiCorp Vault and the built-in VPN clients; WinRM over HTTPS with the certificate checked (plain HTTP only with ?tls=off); SMB shares sign every message and are encrypted when the server asks for it; IKEv1 without 3DES or DH groups below 14 by default; no PAP by default; plain FTP and WebDAV need ?insecure=1, and new plain Redis and memcached conns across the network tooPartly met: new Postgres and MySQL conns across the network check the certificate unless the URL says otherwise; saved conns follow their URL, and doctor warns about those without verified TLS and prints the fix. --legacy-crypto (3DES, DH groups 2 and 5) and --allow-pap turn the weak options back on for one VPN, with a person's yes
12.3 Files: no path traversalFolder downloads refuse server paths that lead outside the targetMet
14.2 Dependencies are known and kept up to dateGo modules, govulncheck in CI, DependabotMet

Limits

What komando does not cover:

  • An AI agent is your own user. komando stops mistakes and injected instructions; it cannot stop a program that runs as you and means harm. Real isolation needs an OS sandbox or a separate user account for the agent.
  • The vault key is not on a hardware key (a YubiKey, a TPM); the OS keychain is the strongest place komando keeps it.
  • The approval window is one click unless you turn on an approval code (komando config approval-code): then it also needs the 6-digit code from your authenticator app.
  • The guard runs only where the agent's harness asks for it. komando guide install sets it up for Claude Code, Cursor, Gemini CLI (v0.26+) and Codex (approve it once in /hooks). It is tested with each one's documented hook input. An agent without hooks gets only the approval window and the masking, and only when komando recognises it: Claude Code, Codex, Cursor, Gemini CLI, or any agent with KOMANDO_AGENT=1 set.
