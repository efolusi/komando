Moving in and moving computers

Bring in the servers and databases you already have, and move everything to another computer.

On this page

  • Import your servers
  • Import what you already have
  • Move to another computer
  • Limits
  • Troubleshooting

Import your servers

komando import ssh-config --dry-run              # see what would be added first
komando import ssh-config                        # servers from ~/.ssh/config
komando import env ./shop/.env --group shop      # DATABASE_URL, REDIS_URL, ... from a .env file
komando export --to komando-backup.json          # save everything (no passwords)
komando import komando komando-backup.json       # on the other computer

Typed alone, komando import asks for the source, then the file.

The import ends with the command that checks what came in:

Next: komando test @shop

Import what you already have

Write komando import SOURCE [FILE]. Without a file, komando reads the usual place for that source.

Flags: -g/--group adds everything imported to a group, and --overwrite replaces entries that already have the same name (on a protected one komando asks you first; an AI agent or a script adds --yes after a person agrees). Without --overwrite, komando skips names it already has.

What happens to passwords

Passwords found in these files go to the vault as <name>-pass. They never appear in komando's list, output or history.

What komando checks

  • Importing the same file again changes nothing. A different database that happens to have the same name gets the next free name (shop-2).
  • Conns get the same TLS default as conn add: a database URL that says nothing about TLS gets TLS that checks the certificate (for example sslmode=verify-full, said in a note), and a redis://, amqp:// or other clear-text URL to another computer is skipped unless it ends in ?insecure=1.
  • With --overwrite, the result lists what it replaced. Without a yes, a protected server, conn or VPN is skipped, in the dry run too.
  • A file cannot turn on what host edit and vpn edit ask a person for: forward_agent on a server that did not lend your ssh-agent before, legacy_crypto or allow_pap on a VPN, and, for a VPN it replaces, a CA it no longer checks the server against or mfa or protection turned off. Each stops with SAFETY_SETTING (exit 6) until you say yes: at your terminal komando asks, a script adds --yes, and an AI agent's yes comes from you in komando's window. Settings in the file are never applied; the result lists them in settings_differ with the command to run.
  • The result names the command that checks what came in in data.next, and a person sees it on stderr: Next: komando test @shop.
  • Servers are checked like host add (ports, users, --via). A bad one is skipped, with the reason. A csv import is stricter: one bad row stops the whole import, and nothing is added.
  • Whatever komando cannot import is listed, with the reason. For example: a .pgpass line with *, a URL kind komando does not know, a Host * pattern (its settings become defaults for the other servers), or an Include file that is missing. HostName %h.example.com is understood.
  • A ProxyCommand runs on this computer, so an AI agent needs a person's yes (--yes and the approval window) to import one. Without it, that server is left out with the reason, the other servers still come in, and the import ends with IMPORT_INCOMPLETE (exit 1).

Coming from PuTTY

PuTTY keeps its sessions in the Windows registry. Export them to a file, then import that file (a dry run first lists what comes in):

reg export HKCU\Software\SimonTatham\PuTTY\Sessions putty.reg
komando import putty putty.reg --dry-run
komando import putty putty.reg

PuTTY keeps no passwords, so set them with komando secret set or use a key. A key in PuTTY's own format (.ppk) is listed: convert it with puttygen KEY.ppk -O private-openssh -o KEY, then komando key add NAME KEY. A session that reaches its server through a proxy is listed too: set the way there with komando host edit NAME --via JUMP.

Coming from MobaXterm

In MobaXterm, right-click User sessions and pick Export all sessions to file, then import that file:

komando import mobaxterm sessions.mxtsessions --dry-run
komando import mobaxterm sessions.mxtsessions

SSH sessions come in with their host, port and user, and the folder a session sits in becomes a group. MobaXterm keeps passwords apart, so set them with komando secret set or use a key.

Coming from Termius or TablePlus

Termius and TablePlus have no open export format. From Termius, export your hosts as an SSH config and run komando import ssh-config FILE. For databases, put their URLs in a .env file and run komando import env FILE.

Move to another computer

There are three ways. An export moves your servers, conns, VPNs, recipes, your own deny rules and settings, but no passwords and no key files: you set those again. A sealed export moves the same with the passwords in one file that opens only with a passphrase you choose. Copying the folder moves everything, passwords included, once the vault has a passphrase.

Export and import (no passwords)

export saves your servers, conns and VPNs, and when you export everything also your saved recipes, your own deny rules (policy deny) and your settings:

komando export --to komando-backup.json       # everything; no passwords
komando export @prod --to prod.json           # only what a target picks (no recipes)
komando export                                # print it instead of writing a file

export writes the file with mode 0600, and refuses to replace an existing file unless you add --overwrite.

On the other computer:

komando import komando komando-backup.json
komando secret set prod-db-pass               # the import lists the passwords to set again

The export file holds no passwords, only their names, so set them again with komando secret set. The import adds your deny rules (they only stop more), but changes no setting: it lists the settings that differ, each with the komando config set command that sets it, because a file from someone else must not turn a check off. When komando refuses something in the file, the rest still comes in and the import ends with IMPORT_INCOMPLETE (exit 1): fix those entries and import again (what is in already is skipped).

Private keys are never in an export file either. When a server logs in with a key from komando key, export names the key (keys_needed) and its file (key_files): copy that file to the other computer yourself. A key komando made (key gen) is sealed in komando and has no file (keys_sealed): make a new one on the other computer with komando key gen NAME and put it on the servers with komando key deploy. The import still adds the server, says which key it needs, and leaves the key out until you bring it (ssh-agent or your default key may log in meanwhile):

komando key add deploy ~/Downloads/deploy     # the copied key file
komando host edit db1 --key deploy

An export file may come from someone else, so komando imports it with these limits:

  • A ProxyCommand is dropped, because it would run on this computer. Set it yourself with komando host edit NAME --proxy-command ....
  • A password reference is kept only if it names a secret: that does not exist here yet. Anything else is dropped, so a file cannot point your existing passwords at its servers.
  • Recipes marked read-only are imported as changes. Mark them read-only again yourself with komando recipe add NAME ... --read-only --overwrite.

Each dropped setting is listed in the result.

A sealed export (everything, with passwords)

--sealed writes the export and the passwords its servers, conns and VPNs use into one sealed file. Only a person at a terminal can make one (an AI agent gets NEEDS_PERSON), and komando asks for a passphrase for the file, twice, hidden:

komando export --sealed --to move.kmdseal                # asks a passphrase (15+ characters)
komando export --sealed --with-keys --to move.kmdseal    # and the private keys the servers use
komando export @prod --sealed --to prod.kmdseal          # only what a target picks
komando export --sealed --to move.kmdseal --dry-run      # what would be sealed; asks nothing
Choose a passphrase for the file: 15 or more characters (random words work).
Passphrase (hidden):
Type it again (hidden):
sealed 2 servers, 1 conn, 2 secrets, 1 key into move.kmdseal (it opens with its passphrase)
check phrase: kangaroo maximum crush write exit shock
Next: komando import komando move.kmdseal (on the other computer; it asks for the passphrase)

The file is written with mode 0600; nothing in it is readable without the passphrase, and changing a byte stops it from opening. A secret a server names that is not in the vault is listed, and stays out. A security key (FIDO2) stays on its device.

On the other computer, the same import reads it and asks for the passphrase once:

komando import komando move.kmdseal
komando import komando move.kmdseal --overwrite   # also replace secrets that are here with another value (asks first)

The import keeps the limits of any export file (below). A password from the file goes into the vault when that name is not here yet. When the vault has that name with another value, it keeps its own, and the file's servers do not get it, unless you add --overwrite and say yes. A key from the file is kept in komando's store, as one key gen made; a key with a name that is here already is left out.

A wrong passphrase, or a file changed after it was sealed, stops with WRONG_PASSPHRASE; a damaged file with SEALED_FILE_INVALID. Nothing is imported then.

Send everything to the iPhone app

From Linux or Windows, with only an iPhone, --for-phone seals the file to a key the iPhone app makes for this one export. Only that phone opens it; the terminal cannot:

komando export --for-phone --to phone.kmdseal

komando asks for the key file the phone shared (or the key itself, as the phone shows it) and the key check the phone shows (64 letters and digits, spaces and dashes do not matter). A key that does not match the key check is refused (PHONE_KEY_INVALID), so a key file swapped on the way is caught. Then it prints a check phrase of six words: move the file to the phone any way you like, and check that the phone shows the same six words. If they differ, do not use the file. The phone reads servers, conns, VPNs, their passwords and, with --with-keys, the keys.

The file is sealed with post-quantum encryption (X-Wing: ML-KEM-768 with X25519), so a copy left in mail or a cloud backup stays closed even to a future quantum computer. It needs the iPhone app for iOS 26 or later. A file made by komando 0.14.0 (X25519 only) no longer opens on the phone, and a key from an older app is refused: update the app and make the file again.

The format is in the sealed file design.

Copy the folder (everything, with passwords)

The vault's key must travel with it, so give the vault a passphrase first. A key in store.key or in the system keychain does not travel: a copied folder whose key stayed in the old computer's keychain cannot open its secrets.

komando secret passphrase                     # on the old computer: type a passphrase (15+ characters)
# copy ~/.komando to the new computer (a USB stick, scp), then there:
export KOMANDO_VAULT_PASS='the passphrase'    # or type it when komando asks
komando doctor                                # the vault opens, the servers are there

On the new computer you can go back to a key file and move it into the keychain: komando secret passphrase --off --yes, then komando secret keychain. Copy SSH key files kept outside ~/.komando (in ~/.ssh) too.

Restore from a backup (Time Machine, a new computer)

A backup of ~/.komando (Time Machine, a disk image, a copy) holds the store, but not always its key. komando doctor says where the key lives; check it before you need the backup:

Key lives inThe backup on this computerThe backup on a new computer
a passphraseopens with the passphraseopens with the passphrase
store.key (inside the folder)opensopens, so treat the backup like the passwords themselves
the OS keychain (the default)opens: the keychain still has the keydoes not open its secrets: the key stayed in the old computer's keychain

So for a backup you can take to a new computer, give the vault a passphrase first (komando secret passphrase), or keep an export next to it and set the passwords again from your password manager.

Put the folder back with komando running nothing (no VPN, tunnel or job started from it; komando status shows them), then:

komando doctor                                # the vault opens, the servers are there

When the key is in the keychain, the keychain also remembers how many changes the store had. A restored copy is older, so every command then stops with STORE_OLD_COPY (exit 6): its servers, rules, secrets or pinned host keys may be out of date, and an old copy put back by someone else looks the same. komando doctor and dry runs still work. If you put it back yourself, accept it in your own terminal (an AI agent cannot):

komando doctor --accept-old-copy

Then check what changed since the backup: servers or rules you added later, and host keys pinned since (komando host trust asks again for a server it no longer knows).

Limits

  • Passwords, private key files and keys komando made never travel in a plain export file; set or copy them on the other computer, or use a sealed export.
  • Only a person at a terminal makes or opens a sealed file. A file for the phone opens only on that phone.
  • An import changes no setting: it lists the ones that differ.
  • A copied folder opens its secrets on another computer only when the vault has a passphrase (or its key is in store.key, inside the folder).
  • A backup put back on the same computer stops with STORE_OLD_COPY until a person runs komando doctor --accept-old-copy, when the key is in the keychain.
  • Termius and TablePlus have no open export format (see above).
